# Revision-bound memory maintenance

Issue: #1407. Status: implementation contract.

## Current boundary

`memory.db` owns active records, revisions, sources, events, and startup injection receipts. Managed `wardian memory` commands authenticate an agent-bound capability and may mutate only that agent's records. Desktop Tauri memory commands use `MemoryActor::Operator`, but the current frontend only reads memory. The registered legacy Tauri `memory_save`, `memory_update`, and `memory_remove` commands are unconfirmed cross-agent write routes. `MemoryStore::update` preserves kind and scope, accepts no expected revision, and replaces the source list supplied by the caller. The existing consolidator batch is agent-scoped and cursor-oriented; it has no user preview or revision guard.

The audit found changing work checkpoints classified as stable, stale status claims still active, and historical task journals competing for the startup budget. It is a bounded sample, not a fleet-wide error rate. The maintenance feature must make a human-reviewed correction possible without granting managed agents cross-agent write access or mutating existing records automatically.

## Decision and authority

A maintenance plan targets exactly one agent owner. A managed agent may prepare a local plan file, but the desktop is the only operator that previews and applies it. The UI imports the file, displays the full before/after and conflicts, and invokes a host command. Apply requires a native user confirmation that names the owner, operation count, and preview digest. The confirmation is enforced by the backend even if a caller bypasses the visible UI. Decline, unavailable UI, or cancelled request makes no memory change. The managed CLI remains owner-scoped; it gets no `--operator` flag, environment escape, or direct database write route.

The plan is reviewable input, never authority. A user applies it after examining the preview. This is the supported cross-agent path once the desktop is rebuilt. The legacy Tauri write commands are removed from the registered command surface; their direct native-test seeding is migrated to the plan flow. Read commands remain registered. A native dialog prevents a silent apply through the new command, while inspection of the complete diff depends on the desktop preview UI. This owner boundary applies to Wardian APIs; it does not sandbox arbitrary same-OS-user code from direct filesystem access. There is no unattended schedule or age-based purge.

## Plan contract

Version 1 JSON has `schema_version: 1`, `plan_id`, `agent_id`, an `idempotency_key`, and 1-100 operations. Full UUIDs are required for existing memory and revision IDs. An existing memory may appear in at most one source operation, except that a `revise` target may also receive `retire_into` sources. The encoded plan is at most 1 MiB; each text or evidence excerpt is at most 8,192 characters, each source locator at most 4,096 characters, and each operation at most 64 source entries. The frontend and core enforce these limits independently. Unknown fields or operation types are rejected. Scope is always an explicit tagged value: `{ "kind": "agent" }` or `{ "kind": "workspace", "path": "<absolute-workspace-path>" }`. The plan cannot change an existing record's owner.

- `revise`: `memory_id`, `expected_revision_id`, full replacement `text`, `kind` (`stable` or `current`), explicit `scope`, `evidence_excerpt`, and optional `add_sources` in the existing `MemorySource` shape. An in-place kind or scope change retains the logical `memory_id` and creates a new revision. Existing sources are inherited and additional sources are deduplicated; source removal is outside version 1. Revisions carry forward `last_verified_at`; changing the label or wording alone does not independently verify the claim.
- `create`: a unique plan-local `client_key`, `text`, `kind`, `scope`, `evidence_excerpt`, and `sources` in the existing `MemorySource` shape. Apply returns the allocated `memory_id` for that key. This supports splitting a mixed durable rule and active checkpoint without inventing an ID during preview.
- `retire`: `memory_id`, `expected_revision_id`, and a nonempty reason. The active record becomes removed; its revisions, evidence, and sources remain in history. Preview highlights retirement without a surviving memory as a separate action, so it cannot be mistaken for consolidation.
- `retire_into`: `memory_id`, `expected_revision_id`, exactly one of `target_memory_id` or `target_client_key`, and `reason`. An existing target also supplies `target_expected_revision_id` unless a `revise` operation in the same plan already names that target and its expected revision. The target must belong to the same owner and remain active after the batch. Its one final new revision inherits all retired records' source locators and records each absorption link.

The target owner cannot change. A workspace-to-agent or agent-to-workspace scope change is explicit in `revise`; omitted scope has no meaning. The UI shows both before and after scope. Scope JSON rejects duplicate `kind` or `path` keys during parsing, rather than choosing a value based on key order. Evidence excerpts and source pointers remain available in history even when active copies are retired. Current-state evidence must identify what was actually checked; an update timestamp alone is not proof of truth.
Self-targeting, target chains or cycles, duplicate source operations, and references to a target retired in the same plan are rejected before preview succeeds.

## Preview and apply

The desktop UI accepts a local JSON file through a browser file input and caps its byte size before parsing. It passes the raw text to `memory_maintenance_parse({ rawJson })`, which enforces the 1 MiB UTF-8 byte limit and deserializes directly into `MemoryMaintenancePlan`, preserving duplicate scope keys for rejection. Only after parsing does the UI validate the returned plan and send it to the existing `memory_maintenance_preview({ plan })` command. The preview command reads the authoritative store without changing memory records, events, or receipts; normal store opening may initialize schema metadata. It resolves every exact owner/revision, validates the plan, and returns canonical operation order, before/after records, source changes, absorption links, conflicts, and `preview_digest`. The digest binds the canonical plan and every expected active revision. Preview does not grant authority or reserve revisions. The UI provides a per-agent entry point and rejects a plan whose owner differs from that agent before offering Apply.

The preview response has `plan_id`, `agent_id`, `operation_count`, `preview_digest`, `changes`, and `conflicts`. Each change has `operation_index`, `op`, optional `before` and `after` record summaries (memory ID, revision ID, text, kind, scope, evidence excerpt, sources), `source_additions`, `absorbed_memory_ids`, and an optional reason. A conflict has `operation_index`, a stable code, and a human-readable explanation; any conflict disables Apply. `memory_maintenance_apply` returns `plan_id`, `agent_id`, `idempotency_key`, `preview_digest`, `applied_at`, and per-operation memory/revision IDs. The frontend displays full summaries and a receipt, not merely the operation count.

`memory_maintenance_apply({ plan, preview_digest })` first calls a core replay lookup keyed by owner, idempotency key, and canonical plan hash; an identical prior receipt returns without another write or dialog, while reuse for different content fails. A new apply obtains native user confirmation through the host dialog plugin, naming the owner ID, operation count, and digest prefix. The dialog is bound to the desktop window; cancellation, timeout, or an unavailable window fails closed. It then opens one immediate database transaction. It revalidates the digest, owner, all expected active revision IDs, targets, scope, and source preservation inside that transaction. Any mismatch rejects the entire batch with a conflict and no partial writes. A successful transaction writes new revisions/removal statuses, source rows, per-record events with plan and absorption provenance, and an idempotent receipt. The receipt and audit events record the actor as `desktop_operator` and confirmation method as `native_dialog`; they do not invent a human account identity. `memory_maintenance_receipt({ agent_id, idempotency_key })` resolves an uncertain client response without replaying the write. A second preview is required after any conflict.

The user can inspect history and receipt after apply. Rollback is a reviewed forward repair from preserved revisions, not deletion of audit history. Managed owner-scoped CLI mutations, Tauri read callers, and existing records remain compatible. Legacy Tauri write callers must use the reviewed plan path. No database migration of current content occurs at installation.

## Acceptance boundaries

Core tests cover one-owner isolation, exact revision conflicts, all-or-nothing failure, idempotent retries, kind and scope revision, source inheritance and absorption, split/retire mapping, malformed or oversized input, and unchanged owner-scoped CLI mutation APIs. UI tests cover complete preview, conflict display, confirmation decline, and post-apply receipt. Tauri command tests inject confirmation results to prove accepted, declined, cancelled, and unavailable paths without a native dialog driver; this test seam does not weaken the production dialog requirement. The existing native memory acceptance test is already manual/opt-in; it must seed through the reviewed plan flow with an operator accepting the real native dialog, then prove Tauri preview/apply wiring. Do not count the injected tests as native dialog acceptance or the manual test as CI coverage. Recall acceptance is tracked separately in #1406, using fresh and resumed briefs and a stable-heavy 12 KB case with a useful current checkpoint. Capture guidance is tracked in #1405.

Only the approved plan is applied. Existing owner memories are not rewritten by this feature release; a separate cleanup owner prepares and verifies each plan against current evidence. Provider handbook files are a different store and are not modified by memory maintenance.
